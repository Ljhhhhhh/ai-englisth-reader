## 1. 产品定位

### 1.1 一句话定义

**不是背单词 App，不是泛读工具，是一个"交互式精读阅读器"。**

目标是通过结构化拆解英文文章，配合翻页式阅读、逐词翻译、重点词汇卡片、语法解析和测试互动，帮助用户在真实语境中深度理解英语。

### 1.2 核心差异点

| 对比对象     | 他们的做法             | 我们的做法                             |
| ------------ | ---------------------- | -------------------------------------- |
| 传统阅读 App | 纯文本，遇到生词自己查 | 逐词可点击翻译，重点词自动标出         |
| 词典         | 孤立背单词，脱离语境   | 在文章中学习，上下文+例句+语法三位一体 |
| 考试类 App   | 以刷题为核心           | 以阅读体验为核心，测试是辅助验证手段   |
| 泛读产品     | 内容海量，读完就走     | 每篇文章深度拆解，吃透一篇胜过泛读十篇 |

### 1.3 目标用户

**核心用户：**

- 有一定英语基础（A2-B1），需要提升阅读理解能力的学习者
- 备考（四六级 / 雅思 / 托福）需要精读训练的人
- 希望在日常阅读中自然积累词汇的成年人

**暂不覆盖：**

- 零基础（需要系统学发音/语法打底）
- 纯应试刷题用户（需求是题库，不是精读）
- 儿童英语启蒙（交互和页面完全另一套逻辑）

## 2. 核心用户场景

### 场景 1：深度阅读一篇文章

用户打开一篇精读文章，像翻 PPT 一样一页一页浏览：

```
第1-N屏：重点词汇卡片（每屏一个单词，发音+词性+释义+原句+举例）
第N+1屏：语法点解析（1-3个核心语法结构）
第N+2屏：长难句拆解（原句+结构分析+翻译）
第N+3屏：文章原文（可点击单词查看翻译）
第N+4屏：理解测试（选择题/判断题验证理解）
最后一屏：全文中文翻译
```

### 场景 2：收藏和管理生词

用户在阅读中点了一个单词，看到翻译觉得需要记，一键收藏到生词本。生词本支持：

- 按文章归类：知道这个词是从哪篇读来的
- 按掌握程度分级：完全掌握 / 模糊 / 生词
- 查看复习历史：什么时候收藏的、复习了几次

### 场景 3：回顾学习数据

用户想看看自己最近读了几篇文章、收藏了多少词、学了多长时间。

### 5.2 数据库模型

```prisma
// 文章表
Article {
  id          UUID       // 唯一标识
  title       String     // 标题
  source      String     // 来源（BBC / Guardian / 自定义等）
  content     Text       // 英文原文
  parsed      String     // 精读 JSON 字符串
  level       String?    // 难度级别 A1-C2
  createdAt   Date
  words       Word[]     // 关联生词
  studyLogs   StudyLog[] // 关联学习记录
}

// 单词表
Word {
  id              UUID
  word            String
  phonetic        String       // 音标
  pos             String       // 词性
  meaning         String
  originalSentence String?      // 原文中的例句
  articleId       UUID         // 来自哪篇文章
  starred         Boolean      // 是否收藏
  masteryLevel    Enum         // new / familiar / learned / mastered
  reviewCount     Int
  lastReviewedAt  Date?
  createdAt       Date
}

// 学习记录
StudyLog {
  id        UUID
  articleId UUID
  duration  Int           // 学习时长（秒）
  startedAt Date
  endedAt   Date
}
```

## 6. 关键交互流程

### 6.1 阅读一篇文章

```
用户点击文章
  → 首先浏览词汇卡片，每屏一个（阅读器第一屏）
  → 然后查看语法解析，每屏一个
  → 进入文章原文阅读界面
  → 向下滑动 / 点击翻页
  → 任何时刻可点击单词查看翻译
  → 浏览测试题
  → 查看全文翻译
  → 阅读完成后提示"是否收藏本文的生词"
  → 自动保存学习记录
```

### 6.2 查看单词翻译

```
用户点击文章中的某个单词
  → 弹出翻译浮窗
  → 显示：单词 + 音标 + 词性 + 中文释义 + 1-2个例句
  → 提供操作按钮：
     · ⭐ 收藏到生词本
     · 🔊 发音（可选）
     · ✕ 关闭浮窗
  → 点击浮窗外部 / 滑动浮窗消失
```

### 6.3 管理生词本

```
进入生词本 → 看到单词列表
  → 支持筛选（按文章 / 按掌握程度 / 按时间）
  → 支持搜索
  → 点击某个单词 → 进入详情页（释义+出处+原句+复习按钮）
  → 支持批量删除和批量标为已掌握
```

## 7. 技术选型原则

### 技术决策的核心原则

**够用就够，不追求大而全。** 当前阶段是单人使用验证产品假设，不应为"未来可能扩展"过度设计。

### 具体选型

| 层     | 选型                 | 理由                                    | 排除理由                                |
| ------ | -------------------- | --------------------------------------- | --------------------------------------- |
| 前端   | Next.js (App Router) | SSR + 路由 + API Routes 一体，生态成熟  | 不需要 React Native（先网页验证）       |
| UI     | Tailwind CSS         | 原子化 CSS 开发快，不需要复杂设计系统   | 不需要组件库（自定义程度要求高）        |
| 滑动   | Swiper.js            | 轻量、手势滑动、翻页动画开箱即用        | 不需要自写（已有成熟方案）              |
| 后端   | Next.js API Routes   | 一个框架全搞定，不需要独立后端服务      | 不需要微服务（没有并发压力）            |
| 数据库 | SQLite + Prisma      | 零运维，文件即数据库，Prisma 有类型安全 | 不需要 PostgreSQL（没有多人并发）       |
| 翻译   | LLM                  | 自由度高，翻译人性化                    | DeepL（收费），不自建翻译模型（没必要） |
| 部署   | Vercel               | Next.js 原生部署平台                    | Docker（增加运维成本）                  |

### 不在 MVP 中引入的

- **用户认证**：单用户，不需要登录系统
- **React Query / SWR**：MVP 数据简单，useState 够用
- **Redis / 缓存**：没有高并发
- **消息队列**：没有异步处理需求
- **独立后端仓库**：API Routes 足够

## 8. 交付计划

### Phase 1：能看到东西（核心验证）

**目标：** 把一篇预解析好的静读文章渲染出来，能翻页、能看翻译。

**产出：**

- [ ] Next.js 项目初始化
- [ ] Prisma 数据库 + 种子数据
- [ ] 静读页面（滑动翻页）
- [ ] 文章原文展示（静态文本）
- [ ] 词汇卡片展示
- [ ] 语法解析卡片展示
- [ ] 理解测试展示
- [ ] 全文翻译

**完成标准：** 部署后能看到完整的静读体验，滑动翻页，内容正确显示。

### Phase 2：能交互

**目标：** 在 Phase 1 基础上加入核心交互。

**产出：**

- [ ] 逐词点击翻译（MyMemory API 代理）
- [ ] 翻译弹窗 UI
- [ ] 一键收藏单词
- [ ] 学习计时器

**完成标准：** 阅读中可随时查看单词翻译并收藏。

### Phase 3：能管理

**目标：** 数据可查、可管理。

**产出：**

- [ ] 生词本页面（列表/筛选/详情）
- [ ] 学习统计页面
- [ ] LLM 自动生成静读数据接口（传入原文 → 输出完整静读 JSON）
- [ ] 文章列表页

**完成标准：** 能够查看已收藏的单词，看到学习数据。

### Phase 4：体验打磨（后续迭代）

**产出：**

- [ ] 复习机制（基于遗忘曲线的复习提醒）
- [ ] 文章难度分级与推荐
- [ ] TTS 语音朗读
- [ ] 响应式适配（手机体验优化）

## 9. 风险与约束

| 风险                   | 影响                      | 应对                                 |
| ---------------------- | ------------------------- | ------------------------------------ |
| LLM 静读数据质量不稳定 | 生成的词汇/语法卡片不可用 | MVP 阶段手动准备数据，验证后再自动化 |
| 翻译 API 调用频率限制  | 大量点击单词可能触发限流  | 前端缓存同一篇文章的翻译结果         |
| 滑动体验不流畅         | 核心产品价值受损          | Swiper 是经过验证的方案，优先保证    |
| 内容版权问题           | 不能随意抓取和分发文章    | MVP 阶段用自有内容，后续考虑开源文章 |

## 10. 关键假设与验证点

### 核心假设

1. **用户真的需要"读"而不是"泛读"** — 通过 Phase 1 上线后的使用数据验证
2. **LLM 能自动生成足够好的静读结构** — Phase 3 验证，不达标则回退到人工
3. **PPT 式翻页是好的阅读交互** — 用户测试反馈

### 验证指标（Phase 1 上线后）

- 用户是否完整读完一篇文章
- 单词翻译的使用频率
- 生词收藏的使用转化率
- 单篇文章平均阅读时长
